# Sign-in and unlock

My Vault uses the established compatible-client encryption model. MyAccounts
identifies you; the vault client still needs its encryption key to unlock.
An unlocked running client keeps working until its ordinary lock policy applies.
Refreshing/reopening the web app can require unlock. No master password or
decryption key is copied from MyAccounts, Workspace or another browser origin.

## With One Workspace

The updated Workspace manager registers a dedicated `workspace-vault` application
in its own MyAccounts instance and saves its settings in the protected vault data
folder. Its distinct callback is:
`https://YOUR-VAULT/identity/connect/oidc-signin`.

1. Open My Vault from Workspace. The client first reuses its own unlocked or
   locked session. If authentication is needed, it starts upstream OIDC
   automatically and reuses your existing MyAccounts browser session.
2. MyAccounts must provide a verified email. Unverified email is refused.
3. On your first visit, the managed integration permits upstream SSO to provision
   your vault account. The compatible client asks you to choose a master password
   and creates the encryption keys. No separate email/login form is required.
4. On later visits, unlock when prompted. This encryption step is separate from
   MyAccounts authentication and follows the vault's ordinary lock policy.

The managed `workspace-vault` configuration sets `provisionAccounts: true`.
Standalone identity configurations retain the default `false` unless the owner
explicitly enables this setting. Provisioning requires successful upstream OIDC,
PKCE and verified email; anonymous registration remains closed. Existing-account
linking still matches the verified email and requires the existing master password.
No encryption password or key is generated by Workspace or MyAccounts.

The integration uses the native engine's canonical SSO organization identifier,
including its first-account password-policy route. A display label in place of
that identifier causes first-time users to bounce back to login. Initialization
must not be called complete solely because identity authentication or the account
shell succeeds. First-password navigation was observed during the local repair;
browser password submission remains a separate acceptance step. See the current
acceptance matrix for historical checks and remaining limits.

## Independent access

Use **Use independent vault sign-in**, or open the vault with
`?login=independent#/login`. Its ordinary email/password controls remain available.
This works with MyAccounts stopped. An SSO association does not remove password
login. Compatible clients use the same independent server URL.

With a dedicated public hostname configured, SSO starts on that public origin.
The direct localhost recovery address presents independent login instead, so its
browser-binding cookie is never incorrectly expected on another origin.

The local owner's **Use independent sign-in only** button saves an opt-out that
Workspace preserves on future starts. Advanced standalone settings accept your
MyAccounts issuer and dedicated client credentials. Remote issuers require trusted
HTTPS; HTTP identity discovery is allowed only on loopback.

Client secrets live outside the executable in protected NTFS `myvault-sso.json`.
They are excluded from independent recovery archives. After restoring a backup,
test direct login before reconnecting an identity provider.

Workspace sign-out does not automatically lock the separate vault origin. Use
the vault's **Lock now** / **Log out** and its session settings on shared PCs.
Provider-only sign-in uses upstream vault sessions after authentication, allowing
access during an identity outage; revoke vault sessions separately when removing
access. No automatic unlocking or custom cryptography is implemented.
